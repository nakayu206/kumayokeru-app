# コード規約

TekuShareプロジェクトの規約をそのまま踏襲する。

## 全般

- Dart公式スタイルガイド(`dart format`)+ `flutter_lints` を採用し、CIでフォーマット/静的解析/テストを自動実行
- 1ファイル1クラスを基本(例外: 密結合な小さなクラス[enumや小ValueObject]は同ファイルでもOK)
- Widgetの分割目安: 100行超・2箇所以上で使用・build()のネストが4階層超
- Pageはデータ取得と画面構成のみ、Widgetは受け取って表示するだけ

## 命名規則

| 種類 | 形式 | 例 |
|---|---|---|
| クラス・enum・型 | UpperCamelCase | `SightingPost`, `SoundType` |
| 変数・関数・引数 | lowerCamelCase | `sightingPost`, `playNotificationSound()` |
| 定数 | lowerCamelCase | `defaultIntervalSeconds` |
| ファイル名 | snake_case | `audio_service.dart` |
| ディレクトリ名 | snake_case | `sighting_map/`, `common_widgets/` |
| Provider | 末尾に`Provider` | `audioSettingsProvider` |
| Notifier | 末尾に`Notifier` | `AudioSettingsNotifier` |
| 画面Widget | 末尾に`Page` | `HomePage` |
| 部品Widget | 末尾に`Widget`または役割名 | `SightingPinWidget` |
| bool変数 | `is` / `has` / `can` で始める | `isNotifying`, `hasOfflineMap` |
| domain層Entity | シンプルな名前 | `SightingPost` |
| data層Model | `Model`サフィックス | `SightingPostModel` |
| UseCase | 動詞+名詞 | `PostSighting`, `PlayNotificationSound` |

## コメントルール

- 言語: 日本語で書く
- ドキュメントコメント(`///`): publicなクラス・関数・プロパティに必ず書く
- インラインコメント: 「なぜそうしているか(why)」を書く。コードの言い直しはNG
- `TODO` / `FIXME` / `NOTE` を用途別に使い分ける

## 非同期処理

- `async/await` を使う(`.then()`チェーンは使わない)
- エラーは`try/catch`で明示的に処理。握りつぶし厳禁(特にバックグラウンド音声再生・GPS取得は失敗時の挙動を必ず定義する)
- 意図的に待たない場合は `unawaited()` で明示

## エラー表示の方針(アプリ全体で共通)

- **入力バリデーション**(未入力・形式不正など、画面から離れずその場で直せるもの): 画面内に赤文字で表示する。
  `presentation/widgets/common/error_text.dart`の`ErrorText`を使う。SnackBarは使わない(スクロールで見逃されるため)。
- **通信・認証エラー**(kumayokeru-backendからのエラー応答、ネットワーク不通など): ダイアログで表示する。
  `presentation/widgets/common/error_dialog.dart`の`showErrorDialog()`を使う。ユーザーに確実に気づいてもらう必要があるため。
- 一覧データの取得失敗(出没情報マップ等、ページ全体のロード失敗)はダイアログではなく画面内表示(`ErrorText`)でよい。
  ユーザー操作(ボタン送信等)に対する応答ではなく、受動的なロード失敗のため。

## importの順序

1. dart標準ライブラリ
2. Flutter
3. 外部パッケージ(pub.dev)
4. 内部パッケージ(プロジェクト内)

グループ間に1行空白を入れる。相対パスは使わず、必ず`package:`絶対パスで書く。

## const

- コンストラクタ引数が全てコンパイル時定数なら積極的に`const`
- Widgetのコンストラクタに`const`をつける(`super.key`も忘れずに)
- `const`: コンパイル時定数(変更不可・再利用される) / `final`: 実行時に1度だけ代入(変更不可)

## アーキテクチャ方針

- クリーンアーキテクチャ(domain / data / presentation / infrastructure / core)を採用(詳細は[全体設計書.md](全体設計書.md)セクション8)
- 状態管理はRiverpod。`watch`は値の変化に応じてUIを再描画したい場合、`read`はボタンタップ等イベント時に1回だけ呼ぶ場合に使う。`build()`内で`read`を使わない
- Providerの定義はクラス内ではなくファイルのトップレベルに

## テストに関する規約

- 新規機能追加時はユニットテストを必須とする(カバレッジ目標: コアロジック80%以上)
- PRと同じタイミングでテストを必ず作成する
- バックグラウンド音声・位置情報などOS依存処理を含むPRは実機テスト結果を添付すること

## レビュー規約

- 全てのPRはレビュー必須(最低1名の承認)
