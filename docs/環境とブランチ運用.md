# 環境とブランチ運用ガイド

このプロジェクトにおける「ビルドモード」「環境(Flavor)」「Gitブランチ運用」の考え方をまとめたドキュメントです。TekuShareでの運用方針を踏襲しています。

---

## 1. Flutterのビルドモード(Debug / Profile / Release)

| モード | 速度 | デバッグ | ホットリロード | 用途 |
|---|---|---|---|---|
| Debug | 遅い | ◎ | ◎ | 開発中 |
| Profile | 速い | △ | ✗ | 性能測定 |
| Release | 最速 | ✗ | ✗ | ユーザーに配布 |

「開発しやすさ」と「速さ」は両立できないので、目的別にモードを切り替える。

## 2. 環境(Flavor: dev / stg / prod)

ビルドモードとは別に、**接続先や設定を切り替える仕組み**として「Flavor」がある。

| Flavor | 用途 | Android applicationId | iOS BUNDLE_ID_SUFFIX |
|---|---|---|---|
| dev(Development) | 開発者が自由に壊していい環境 | `com.kumayokeru.app.dev` | `.dev` |
| stg(Staging) | 本番同等構成。QA・テスター用 | `com.kumayokeru.app.stg` | `.stg` |
| prod(Production) | 本番。絶対に壊さない | `com.kumayokeru.app` | (なし) |

### このプロジェクトでの実装

| ファイル | Flavor | 用途 |
|---|---|---|
| `lib/main_dev.dart` | dev | 開発用 |
| `lib/main_stg.dart` | stg | 検証用 |
| `lib/main_prod.dart` | prod | 本番用 |

Android側は `android/app/build.gradle.kts` の `productFlavors` で定義済み。
iOS側は `ios/Flutter/<Debug|Release|Profile>-<dev|stg|prod>.xcconfig` を作成済みだが、
Xcode上のBuild Configuration/Scheme作成はMac作業待ち([ios/FLAVOR_SETUP.md](../ios/FLAVOR_SETUP.md)参照)。

## 3. テストはどの環境でやるべきか

| テストの種類 | やる場所 | 誰が | 何を確認? |
|---|---|---|---|
| ユニットテスト | ローカル | 開発者 | 関数1つが正しく動くか |
| ウィジェットテスト | ローカル | 開発者 | UI部品が正しく表示されるか |
| 結合テスト(開発中) | dev | 開発者 | 機能を作りながら動作確認 |
| QA / 受け入れテスト | stg | QA・テスター | 本番同等の環境で総合確認 |
| 本番動作確認(スモーク) | prod | 開発者・運用 | リリース後に最低限動くか |

```bash
# 開発中の動作確認
flutter run --flavor dev -t lib/main_dev.dart

# リリース前のテスト
flutter run --flavor stg -t lib/main_stg.dart

# 本番ビルド
flutter run --flavor prod -t lib/main_prod.dart --release
```

## 4. 環境ごとにGitブランチを分けるべきか

**結論: 環境ごとに長命ブランチを作る運用(dev/stg/prodブランチ)は非推奨。「単一のmainブランチ + Flavor + CI/CD」が業界標準。**

根拠(GitHub Flow、Git Flow提唱者本人の追記、ThoughtWorks Technology Radar、Google DORA、Martin Fowler、The Twelve-Factor App 等)は割愛するが、環境別ブランチには以下のデメリットがある。

- マージ漏れ(stgで直したのにprodに反映されてない)
- ブランチ間の差分でバグが起きる
- hotfixを複数ブランチ全部に当てる必要がある
- 「どのブランチに何が入ってる?」が不明瞭

## 5. mainブランチ1本からstg / prodをどう出し分けるか

ブランチでは分けず、**「タグ」+「CI/CD」**で出し分ける(GitHub Flow + タグリリース)。

```
main ──●──●──●──●──●──●──●──
       │     │        │
       ▼     ▼        ▼
     [自動]  v1.0.0  v1.1.0   ← タグ = prodリリース
      stg   (prod)   (prod)
```

| トリガー | デプロイ先 |
|---|---|
| `main` へのpush | stgに自動ビルド(`.github/workflows/deploy-stg.yml`) |
| `v*.*.*` タグのpush | prodに自動ビルド + GitHub Release作成(`.github/workflows/deploy-prod.yml`) |

### 運用フロー

```bash
# 1. 機能開発
git checkout -b feature/xxx
git push origin feature/xxx
# → PR作成 → ci.ymlが自動でtest/analyze実行 → レビュー → mainマージ

# 2. mainマージ → deploy-stg.ymlが自動でstgビルド

# 3. 本番リリース
git checkout main
git pull
git tag v1.0.0
git push origin v1.0.0
# → deploy-prod.ymlが自動でprodビルド + GitHub Release
```

## 6. このプロジェクトでの推奨運用まとめ

### ブランチ戦略: GitHub Flow + タグリリース

```
main                    ← これ1本でOK
  ├─ feature/xxx        ← 機能開発(短命)
  └─ fix/xxx             ← バグ修正(短命)
```

- 環境別の長命ブランチは作らない
- 全てのPRはレビュー必須(最低1名の承認、[コード規約.md](コード規約.md)参照)

### 役割整理

| | 役割 |
|---|---|
| Gitブランチ・タグ | コード履歴の管理 |
| Flavor(dev/stg/prod) | ビルド設定の切り替え |
| CI/CD | ブランチ→環境への自動デプロイ |

> 「ブランチで環境を分ける」のではなく、「ブランチの状態 = どの環境にデプロイするか」をCI/CDで決める。
